# R2 — City Permits Resident Portal

## 1. Design Brief

```
DESIGN BRIEF
- Use case: Residents of a city permits office check the status of their permit applications and submit reviewer-requested documents (occasional use, all ages, desktop + phone).
- Pattern + variant: portals / consumer account home (status + documents self-service)   [Stage 1: S16 — external, occasional, one account + statuses]
- Recipe: Institutional Blue *(primary; alt Calm Clinical not needed — government temperature wants the bank-statement register)*  ·  Density: 3 (account-home stance; ~6 zones and ~18 values per desktop viewport, STANDARD card padding)        [Stage 2: occasional-customer × institutional-trusted]
- Palette (5+ hexes): page #FAFCFF, cards #ffffff (shadow-not-border), brand/accent #1155cc (band + UNDER REVIEW tag + list bullets — one hue, three jobs), semantic #38761d (APPROVED tag + completed timeline stamps) and #c9243f (ACTION NEEDED — the page's single alarm hue: tag, action-card top bar, current timeline stamp), band subtitle #ffe599, upcoming-step gray #b7b7b7, labels SECONDARY token.
- Header treatment: card-in-card full-bleed #1155cc brand band (white outer card padding NONE wrapping brand card padding MORE, contentsPadding NONE) — no photo billboard; the band itself answers task #1 with a "1 needs your attention · 1 under review · 1 approved" summary line before any scroll.
- Signature moves (≥3, from recipe or anti-corporate menu):
  1. One-hue monopoly — #1155cc does header band, in-process status tag, and document bullets; no second brand hue anywhere (recipe move 1 / menu #6). Lever: cardLayout style + tagItem backgroundColor + richTextIcon color sharing one hex.
  2. Rationed alarm — #c9243f appears only as the ACTION NEEDED state, hue-coded twice at linked locations (status tag on the deck-permit row, decorativeBar TOP on the upload card, current stamp on its timeline); no red buttons, no red decoration (menu #8, quote-review's twice-applied state hue). Lever: tagItem backgroundColor + decorativeBarPosition/Color + stampField backgroundColor.
  3. Drill-in rows instead of grids — each application is a whole-card a!cardLayout(link:) shadow card with trailing angle-right-bold chevron, generated by a!forEach; linked cards stay display-only (recipe move 4 / menu #19). Lever: cardLayout(link: a!dynamicLink) + showShadow true/showBorder false.
  4. Repeated-record grammar — caps eyebrow sectionLayouts (SMALL/SECONDARY/H3) over STRONG values with right-pinned meta via sideBySide width MINIMIZE and divider BELOW; amount-free fact pairs (type | review days, tag | submitted date) share one scan line (recipe move 2 / menu #11 + #14). Lever: sectionLayout label params + sideBySideItem width "MINIMIZE".
  5. Hand-built numbered status timeline — TINY stampFields carrying step numerals ("1"–"4": green done, red current-action, gray upcoming) beside STRONG step + SMALL date rows, answering "where am I / how long?" with per-step dates a stock milestone can't show (menu #23 / cookbook 5.3, sideBySide flavor). Lever: stampField text/backgroundColor/accessibilityText in sideBySide rows.
- Deliberately omitted: photo hero and any navigation chrome (hamburger/menu/tab bar) — an occasional, all-ages resident arrives to do exactly two things; a billboard would cost phone load time the task never repays, and the portal pattern's "boring twin" warning is precisely a menu nobody anonymous needs. The brand band plus two content zones serve both tasks with zero wayfinding.
```

Portal-specific rules honored: every displayed time carries its zone ("9:40 AM (ET)", counter hours "(ET)"); no `a!isNativeMobile()` — responsiveness is `a!isPageWidth()` + `stackWhen` only; content is capped and centered (WIDE_PLUS column between empty AUTO flanks) because portals render at Full width; the page bottom-right stays clear of submit controls (reCAPTCHA corner — the one SOLID button sits mid-page in the left column).

```
         │     ├─ SBS [TAG(status: #c9243f | #1155cc | #38761d) | "Submitted <date>" SMALL SECONDARY → right]
         │     ├─ permitType MEDIUM_PLUS STRONG + char(10) + scope MEDIUM
         │     │  + char(10) + "<ref> · <address>" SMALL SECONDARY
         │     └─ SBS [next-step sentence | chevron angle-right-bold → right]
         └─ RAIL (MEDIUM)
            ├─ SECTION "Deck Permit Progress" (H2)
            │  └─ CARD(shadow) → forEach ×4:
            │        SBS [STAMP numeral TINY (#38761d done ×2 · #c9243f current · #b7b7b7 next)
            │             | step STRONG + char(10) + date/meta SMALL SECONDARY]
            └─ SECTION "Permits Office" (H2)
               └─ CARD(shadow)
                  ├─ eyebrow "VISIT" → address STRONG + hours "Mon–Fri, 8:00 AM–4:30 PM (ET)"
                  ├─ eyebrow "CONTACT" → 5.6 rows [Phone | (555) 014-2960 → right] [Email | permits@alderbrook.gov]
                  ├─ eyebrow "TYPICAL REVIEW TIMES" → forEach ×3 [permit type | days STRONG → right]
                  └─ "Start a New Application" STANDALONE link (quiet — recipe keeps buttons to the one CTA)
```

Phone behavior (portal = `a!isPageWidth` + `stackWhen` only): both columns layouts stack at PHONE/TABLET_PORTRAIT and the empty flanks hide (`showWhen: not(a!isPageWidth(...))`), so the read order becomes band → action card → applications → timeline → office — act first, scan second, help last. The submit button flips to `width: "FILL"` on phone; no fixed header; no grids or wide tab strips to fracture.
